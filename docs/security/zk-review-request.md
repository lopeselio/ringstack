# Review request: zk-gadgets, template and milestone escrow

We are asking for an external review of the ZK circuits and onchain programs in `zk/` before anyone uses them with real funds. This page is the brief: what is in scope, what we assume, what we checked and how, and the questions we cannot answer ourselves. Everything runs on Helius Privacy devnet today; nothing is audited.

## Scope

| Path | What it is | Size |
|---|---|---|
| [`zk/gadgets`](../../zk/gadgets) | `threshold` (M-of-N approvals), `allowlist` (Poseidon Merkle membership), `timelock` (program-side clock checks), and the test harness | 77 / 1,220 constraints |
| [`zk/template`](../../zk/template) | A timelocked vault adapted from upstream's timelock escrow: `lock`, `release` | 14,880 / 5,638 |
| [`zk/milestone-escrow`](../../zk/milestone-escrow) | Tranches released by M of N approvers, refund after a deadline: `create`, `release`, `refund` | 16,279 / 11,813 / 6,121 |

For each program: the circuits (`src/circuits/`), the instruction handlers (`src/instructions/`), and how they bind together through the generated verifier modules (`src/verifier/`, generated by `zolana build-zk-program`, not hand-written). The TypeScript clients are in scope only where a client mistake could lose funds or privacy (signer ordering, the escrow viewing key).

Out of scope: the shielded pool program, its circuits and prover, `spr-program` and its DSL, and Solana itself. We depend on them; see the assumptions.

Built on `spr-program` 0.8.0 (crates.io), `@heliuslabs/spr` 0.9.0-alpha, Rust 1.98.1. Deployed on devnet: template `3bzWnoteJaH7kD6Jron7Lb1ABfQxLGSqcEzRr3Zy6cAi`, escrow `2XdkS7kQQcuCXQBhQv634B8PhDqFbpTPecHqMavwtMBR`.

## How a call works

A program's proof and the pool's proof cover the same transaction: both commit to one `private_tx_hash`. The program verifies its own Groth16 proof against public inputs it computes itself (the signer's identity, the clock-checked deadline, signer slots), then CPIs `transact` into the pool from a PDA it signs for. The pool verifies its proof and appends the outputs. A program proof is therefore only as strong as two bindings: its public inputs to what the program checks, and its UTXO data to the committed terms.

## Threat model

Adversaries we design against:

- **A malicious prover**, meaning whoever builds a transaction. They choose every private input and may run any client. They do not hold other parties' signing keys.
- **A malicious transaction sender**, who chooses the accounts and their order, the instruction data, and which signers to include.
- **Other pool users**, who can publish outputs carrying any view tag, including an escrow authority's (public) tag.
- For the escrow, any single party: the funder who stops cooperating, the payee who tries to take more than a tranche, an approver who signs twice, an outsider holding the escrow's viewing key.

## Assumptions we trust and do not test

1. **The shielded pool program and its proof** enforce UTXO ownership, nullifiers (no double spend), conservation, and that the program's PDA signed for the PDA-owned inputs.
2. **The DSL** (`spr-program` / `spr-zk-dsl` 0.8.0) compiles each check into constraints as its documentation says: range checks, comparisons, `transfer` balance checks, and `DataUtxo` data-hash binding.
3. **The keys.** The committed proving and verifying keys come from a **single-party setup** (`zolana build-zk-program` without `--test`). Whoever ran it could forge proofs if they kept the randomness. Production needs a ceremony (`zolana zk import`); this is a known gap, not a question.
4. **The Solana clock** (`Clock::unix_timestamp`) is honest within the network's usual drift.

## Invariants to check

Each circuit rule below has a negative test that must fail natively *with that rule's name* and leave the R1CS unsatisfied.

**threshold** (`zk/gadgets/src/threshold.rs`). M ≥ 1. Every non-empty signer is in the approver set. No non-empty signer appears twice. The number of non-empty signers is ≥ M. Contract: the caller binds the approver set and M to committed terms. The gadget alone leaves unused approver slots unconstrained, and a test pins that.

**allowlist** (`zk/gadgets/src/allowlist.rs`). The index is range-checked to the tree depth. Leaves (`poseidon([id])`) and inner nodes (`poseidon([l, r])`) use different Poseidon arities, so a leaf cannot pass for a node. The recomputed root equals the given root.

**Escrow create.** The funder owns the inputs. Amount ≠ 0, tranche ≠ 0, tranche ≤ amount, M ≥ 1. Listed approvers are distinct and number at least M. `escrow_address` is set to where the escrow is created. The deadline is public, and the program refuses one already past.

**Escrow release.** The escrow input matches its committed terms. The funder identity, deadline, payee address hash and escrow address match them. The threshold check runs over the *committed* set against signer slots *the program* computes from the accounts that signed. The escrow is not empty. It pays `min(tranche, what is left)` to the committed payee. The remainder is re-created at the committed escrow address. The program allows it while `now ≤ deadline`.

**Escrow refund.** The funder identity and deadline match the terms. Everything goes to the committed funder. The program allows it once `now > deadline`. A unit test checks the two clock checks are exact complements.

## Evidence

All reproducible with the commands below.

- **Negative cases per rule** in each crate's `tests/`, through the [harness](../../zk/gadgets#the-harness). A case passes only if it is refused natively by the named rule *and* the R1CS is unsatisfied, or it is flagged as never generated. The harness's own tests show it catches a missing bound, a native-only check, a case refused by the wrong rule, and an unused input.
- **No free private variables** in any program circuit, checked on several witness shapes. Upstream's perturbation check (`check_private_variables`) tolerates only UTXO metadata the pool's proof validates and equality-test inverse hints.
- **Property tests** against plain-Rust models for the circuits: threshold (random sets, thresholds, signers), allowlist (random members, claims, indices past the tree), escrow release (random thresholds and signer slots). Each case must agree with the model natively *and* in R1CS, and a rejected case must leave the R1CS generated and unsatisfied, not merely ungenerated. The timelock has no circuit: its property tests the program-side functions at clocks within a few seconds of the deadline, against wide-integer arithmetic. Mutation runs confirm they bite: dropping the duplicate-signer check, the allowlist's index range check, or making `is_unlocked` inclusive fails with a shrunk counterexample, kept as a regression seed.
- **Program verifier binding**: the escrow's release proof is refused when the program sees fewer signers, the same signers reordered, or a different deadline. Every circuit's verifier module is regenerated and compared byte for byte with the committed one (`--check`).
- **Devnet end to end**: the escrow e2e runs two 2-of-3 releases (one built by the payee) and a refund. It shows onchain refusals for an already-expired escrow (9006), a proof for signers who did not all sign (9000), an early refund (9005) and a late release (9006), with exact final balances.
- **A formal uniqueness check, inconclusive.** `zk/scripts/picus.sh` runs Picus ([Veridise/Picus@138b151](https://github.com/Veridise/Picus/tree/138b151d3a388e5b6c040c163e0a1db04f2ceda6)) on each exported circuit and reads run-picus's exit code as upstream's harness does: 8 safe, 9 unsafe (the script then exits 1), 0 unknown, meaning Picus finished but could not decide, for instance because SMT queries hit their per-query timeout. A run still going at the per-circuit limit is killed and also reported unknown. Picus decided neither gadget, so there is no counterexample and no proof:

  |---|---:|---|---|---|---|
  | `threshold-only` | 77 | Picus finished, undecided | Picus finished after 17 min, undecided | killed at the limit | Picus finished after 3 h 19 min, undecided |
  | `allowlist-depth4` | 1,220 | killed at the limit | killed at the limit | killed at the limit | not run |

  The CI columns are runs [42405825409](https://github.com/lopeselio/ringstack/actions/runs/42405825409) and [42410802755](https://github.com/lopeselio/ringstack/actions/runs/42410802755) (2026-11-07) and [42509769928](https://github.com/lopeselio/ringstack/actions/runs/42509769928) (2026-11-08, `threshold-only` alone); GitHub keeps their logs and artifacts for 90 days, so until early February 2027. With 5 s per query, Picus finished `threshold-only` after 17 minutes and reported it could not decide (exit 0), which short query timeouts can cause; with 60 s per query it was still running when the hour ran out, so the circuit limit stopped it. Given 5.5 hours at 60 s per query, Picus finished after 3 h 19 min and again could not decide (exit 0), with over two hours to spare. A 12 times longer query timeout did not decide it either, so neither more time per query nor more time per circuit looks likely to; why Picus gives up is not known. The escrow circuits (6,000 to 16,000 constraints) were not attempted. Whether every wire is uniquely determined therefore rests on the free-variable check and the property tests above, and is a question for the reviewer.

## Questions for the reviewer

1. **Signer slots and account order.** The program fills the public signer slots in account order. The circuit is order-insensitive, but the public hash is not, so the client must list approvers in account order. Is there any way for a sender to make the program compute slots that pass the verifier but differ from who actually signed? Duplicate accounts, an approver who is also the payer?
2. **Tolerated variables.** Is it sound to leave the equality-test inverse hints and the UTXO `nullifier` / `latest_tree_id` metadata to the pool's proof, as upstream's check assumes, in a program that spends a PDA-owned UTXO?
3. **The escrow viewing key** is shared out of band between the funder and the payee, and committed through `escrow_address`. Anything we miss? For example, a payee who leaks the key, or a funder who creates the escrow under a key the payee never receives. The payee can verify the terms only if they have the key.
4. **The zero-value continuation.** After the last tranche, the escrow continues as a zero-amount UTXO until the refund closes it, and releases from it are refused. Any way to abuse a zero-amount PDA-owned data UTXO?
5. **Approver identity.** Signers are identified by `solana_owner_identity(address)`, the same function the pool uses for owners. Any collision or domain concern in reusing it as an approver identity?
6. **`find_program_address` onchain** per instruction, as upstream does. Is there a reason to pass and check the bump instead, beyond compute?

## Reproduce

```bash
cd zk
cargo test --release --features harness              # all circuit, property and program tests
zolana build-zk-program -p milestone-escrow --check   # verifier modules match circuits and keys
zolana build-zk-program -p zk-template --check
PICUS_SOLVER=z3 scripts/picus.sh [--all]              # native run-picus (Racket) with z3
cd .. && ZOLANA_NETWORK=devnet ZOLANA_FUNDER_KEYPAIR=.devnet/funder.json \
  pnpm --filter @ringstack/milestone-escrow-client e2e
```

`picus.sh` defaults to cvc5, which needs a build with finite-field support; Picus's Docker image has one but is x86 only. Use it with `PICUS=scripts/picus-docker.sh` on an x86 machine, or dispatch the `picus` workflow, whose inputs set the circuit limit, the query timeout and the escrow circuits. The CI runs above were:

```bash
gh workflow run picus.yml -f limit_s=1500 -f query_ms=5000
gh workflow run picus.yml -f limit_s=3600 -f query_ms=60000
gh workflow run picus.yml -f circuits=threshold-only -f limit_s=19800 -f query_ms=60000   # one circuit, 5.5 h
```

Copy each crate's committed keys into `target/zk/<crate>/` before `--check` (see the [template README](../../zk/template#build)).

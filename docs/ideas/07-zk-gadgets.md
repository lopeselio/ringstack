# 7. zk-gadgets: building blocks + template for SPP ZK programs

**Status:** Selected (hard pick), in progress: [Z0 done](../spikes/z0-zk-dsl.md) · **Type:** ZK program infrastructure (Rust: `spr-program` DSL + Pinocchio)

## Problem

"ZK Solana programs" are how Helius Privacy becomes programmable (private escrow, swaps, lending, staking). Upstream now has a Rust DSL for them ([`spr-program`](https://crates.io/crates/spr-program) 0.8): a circuit is written once in Rust and runs natively on the client and as R1CS in the prover, and the DSL already handles UTXO hashing, ownership, conservation and range checks. Its one reference program is a single-party timelock escrow.

What is still left to every team:

1. Patterns beyond one owner: M-of-N approvals, allowlists, multi-stage release. Each means binding something committed in a UTXO's data to what the program checks onchain, and that binding is where circuits go wrong (a value the circuit never constrains, a public input the program never checks).
2. Wiring: the program crate, its circuits, the committed verifier modules, the client and a devnet test harness, copied from `sdk-tests/timelock-escrow` and adapted by hand.

## Solution

### A. `zk/gadgets`: a Rust crate on `spr-program`

| Piece | Purpose |
|---|---|
| `terms` | Commit app terms in a UTXO's data and bind each term the program enforces to a public input, so the circuit and the program cannot disagree |
| `timelock` | The pattern from upstream: the unlock time is a committed term, exposed as a public input, checked against `Clock` by the program; helpers for both sides |
| `threshold` | M-of-N approvals: the approver set is hashed into the terms, the circuit proves the signers are distinct members and at least M, the program checks they signed |
| `allowlist` | Membership of an address in a set committed as a Poseidon Merkle root |

Each piece has positive tests, negative tests that must fail with the named rule, and constraint counts. Range checks, comparisons and conservation come from the DSL and are not rebuilt.

### B. `zk/template`: a starter

- Pinocchio program: verify the program's proof, check the public terms, CPI `transact` into the pool from a PDA.
- Circuits crate using the gadgets, with verifier modules generated by `zolana build-zk-program` and checked in CI with `--check`.
- Client and a devnet test (the 0.8 local stack is not published).

### C. Reference program

**Milestone escrow:** a funder locks a private balance released in tranches when M of N approvers sign off, with a timelock refund to the funder. Overlaps with [idea 8](08-sealed-bid-milestone-escrow.md).

## Helius primitives used

`spr-program` (`circuit`, `client`, `cpi`, `compression`, `verifier`), PDA-owned UTXOs, UTXO data, the SPP `transact` CPI, Groth16 verification onchain, `zolana build-zk-program`.

## Risks / open questions

- **Alpha churn:** pin `spr-program` 0.8.0 and track releases; upstream's reference program is the spec.
- **Security:** circuits are easy to under-constrain. Negative tests per rule, property tests, Picus (`export_picus_r1cs`), and an external review before anyone uses this with real funds.
- **Cost:** Groth16 verification plus the CPI per instruction; compare compute and constraints against the timelock escrow baseline (escrow 14,880 constraints, withdraw 5,638).
- **No local stack for 0.8:** end-to-end tests run on devnet, and each program deployment locks rent.
- Licensing: keep compatible with Apache-2.0 upstream.

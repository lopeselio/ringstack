# zk-template

A starting point for an SPP ZK program on upstream's circuit DSL ([`spr-program`](https://crates.io/crates/spr-program) 0.8): the onchain program, its circuits, the verifier modules generated from them, proving keys, a TypeScript client and a devnet end-to-end test. Copy this directory to start a program.

The example program is a timelocked vault. A creator locks shielded tokens in a UTXO owned by a per-creator PDA. After the unlock time, the creator releases them back. It is adapted from upstream's `sdk-tests/timelock-escrow` (helius-labs/zolana, Apache-2.0) to build outside upstream's workspace on the published crates, and its release instruction checks the clock with [`ringstack-zk-gadgets`](../gadgets)' `timelock::is_unlocked`.

## How a call works

1. The client builds the program transaction with the circuits compiled to wasm (`lockTransaction`), and proves it locally with the committed proving key.
2. It gets the pool's own proof of the same transaction from the SDK's prover (`client.proveTransact`). Both proofs commit to one `private_tx_hash`.
3. It sends one instruction. The program verifies its proof with the generated verifier module, checks the public terms (the creator's signature; for release, the clock), and CPIs `transact` into the pool from the vault authority PDA.

## Layout

| Path | What it is |
|---|---|
| `src/circuits/` | `lock` and `release` circuits and the `VaultTerms` state committed in the vault UTXO |
| `src/instructions/` | The onchain handlers: parse, check, verify, CPI |
| `src/verifier/` | Generated by `zolana build-zk-program`; committed, never edited by hand |
| `keys/` | The proving keys the verifier modules were generated with, and their SHA-256 |
| `tests/circuits.rs` | Proves lock and release with the committed keys and verifies them as the program does; a negative case per circuit rule |
| `client/` | TypeScript client (`src/vault.ts`) and the devnet e2e (`scripts/e2e.ts`) |

## Build

Tools: Rust 1.98.1 (pinned in `zk/rust-toolchain.toml`), the `wasm32-unknown-unknown` target, `wasm-pack`, the Solana CLI with `cargo build-sbf`, and upstream's CLI built from the tag the crates come from:

```bash
cargo install --git https://github.com/helius-labs/zolana --tag rust-sdk-v0.8.0 spr-cli --locked
cargo install wasm-pack --version 0.13.1 --locked
rustup target add wasm32-unknown-unknown
```

From `zk/`:

```bash
# The CLI reuses keys found in target/zk/zk-template; put the committed ones there first.
mkdir -p target/zk/zk-template && cp template/keys/* target/zk/zk-template/
zolana build-zk-program -p zk-template --single-threaded --wasm-target nodejs
zolana build-zk-program -p zk-template --check   # verifier modules match the circuits and keys
cargo test --release -p zk-template --features harness
```

That writes the `.r1cs` files, the verifier modules, the Node wasm module (`target/zk/zk-template/wasm`) and the program (`target/deploy/zk_template.so`). The entrypoint is on whenever the crate is built for Solana, so no extra feature is needed for a deployable program. `--single-threaded` avoids the nightly toolchain the threaded wasm prover needs.

Constraint counts match upstream's escrow: lock 14,880, release 5,638.

## Keys and what they promise

The keys in `keys/` come from a **single-party setup** with fresh randomness (`zolana build-zk-program` without `--test`). Whoever ran the setup could have kept that randomness and could forge proofs, and upstream marks every local setup `InsecureTest`: the verifier modules only compile with the `insecure-test-setup` feature. That is acceptable for devnet and for this template, not for real funds. Production keys come from a multi-party ceremony imported with `zolana zk import`.

Never deploy with `--test` keys: their randomness is a public fixed seed, so anyone can forge a proof.

The proving key is public by design; only the setup randomness has to stay secret. It is committed so the verifier modules, the deployed program and every client agree on one key pair. Regenerating keys means regenerating the verifier modules and redeploying.

## Deploy and test on devnet

The program ID in `src/lib.rs` (`declare_id!`) and `client/src/vault.ts` must be the address of the keypair you deploy with:

```bash
solana program deploy zk/target/deploy/zk_template.so \
  --program-id .devnet/zk-template-program.json \
  --keypair .devnet/funder.json --upgrade-authority .devnet/funder.json -u devnet

ZOLANA_NETWORK=devnet ZOLANA_FUNDER_KEYPAIR=.devnet/funder.json \
  pnpm --filter @ringstack/zk-template-client e2e
```

This repo's deployment is `3bzWnoteJaH7kD6Jron7Lb1ABfQxLGSqcEzRr3Zy6cAi` on devnet; the e2e passed against it on 2026-11-06 in about 55 seconds.

An 88 KB program locks about 0.45 SOL of rent; `solana program close` returns it. The e2e deposits 0.01 SOL into the pool, locks 0.007 SOL until about 40 seconds later, checks that a release before then is refused onchain with `NotYetUnlocked` (9005), waits, releases, and checks the balance is whole and no vault is open. The pool's proofs come from Helius's devnet prover; the program's proofs are made locally from `keys/`.

## Starting your own program

1. Copy `zk/template` and rename the crate.
2. Generate a program keypair (`solana-keygen new -o <file>`), and put its address in `declare_id!` and in the client.
3. Change the circuits, state and instructions. Every term the program enforces needs a binding line in the circuit, a named rule and a negative test; see the [binding pattern](../gadgets/README.md#the-binding-pattern).
4. Delete `keys/`, run `zolana build-zk-program` to generate new keys and verifier modules, and commit both.

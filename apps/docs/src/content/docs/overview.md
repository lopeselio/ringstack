## One payment, end to end

1. **Request.** The shop's backend creates an order and encodes a [`ringpay:` request](../reference/ringpay-uri/) with the amount and order number, then shows it as a QR code.
2. **Pay.** The customer's wallet checks the shop is registered for private payments, then sends a private transfer. The order number travels as `order:<id>` in the encrypted memo on the shop's output.
3. **Detect.** [ringd](../tools/ringd/), running next to the shop's backend, holds only the shop's viewing and nullifier keys. It decrypts the new output and records a `payment.received` event with the memo.
4. **Notify.** ringd posts the event to the shop's webhook, signed with HMAC and retried until it lands. The backend verifies it with [`@ringstack/ringd-client`](../reference/ringd-client/), reads the order from the memo, and marks the order paid. The [checkout demo](../tools/checkout-demo/) is this loop, running.
5. **Prove.** The customer can share a [receipt](../reference/receipt-format/) that opens the transaction. A payee in a batch can share a [payment proof](../reference/payment-proof/) that opens only their output. Anyone can check either in the [verifier page](../tools/verifier/).

[Payroll](../tools/payroll/) is the same machinery in bulk: one transaction pays up to 15 people, each with their own memo. The treasury produces an audit bundle for the accountant, and each employee can prove their own pay.

## Packages

| Package | What it does |
|---|---|
| `@ringstack/core` | Wallet sessions (`RingSession`): register, deposit, transfer with memos, batch payouts, withdraw, merge. Also `ringpay:` requests, receipts, payment proofs, and devnet configuration. |
| `@ringstack/ringd-client` | Webhook event types, signing and `verifyWebhook`. |
| `apps/ringd` | The watcher daemon and its CLI. |
| `apps/payroll` | The payroll CLI: `plan`, `run`, `audit`, `prove`. |
| `@ringstack/paywall`, `apps/agent-mcp` | The HTTP 402 paywall and the MCP agent wallet with spend limits. |
| `@ringstack/leakscan`, `apps/leaks` | The leak analyzer CLI and the daily aggregate report page. |
| `@ringstack/derivation-guard` | `isTsppDerivationRequest` for wallets, test vectors, and a page guard for Wallet Standard and injected providers. |
| `apps/derivation-guard-extension` | The browser extension that runs the guard in every page. |
| `apps/verifier` | The static verifier page (Vite). |
| `apps/checkout-demo`, `apps/checkout-api` | The demo shop (Next.js) and its backend (NestJS on Fastify). |

## Trust model in one paragraph

Amounts, assets and memos are encrypted onchain and bound to commitments that the program verifies with zero-knowledge proofs. Proofs are generated by Helius's prover inside an AWS Nitro enclave. The client only talks to an enclave that attests to a policy Helius signs, so the prover sees your private inputs inside the enclave and nowhere else. Who transacts with whom stays visible. The [privacy limits](../guides/privacy/) page lists exactly what is and is not hidden.

## Built on

[Helius Privacy](https://www.helius.dev/privacy), the zolana shielded pool, through the TypeScript SDK `@heliuslabs/spr` 0.9 (published as `@heliuslabs/zolana` before 0.9). Memos travel as encrypted transaction messages ([zolana#543](https://github.com/helius-labs/zolana/issues/543)), so received payments spend through the SDK's own builders. There is no 0.8 local stack yet, so integration tests run on devnet. Details are in the [SDK findings](../background/sdk-findings/).
